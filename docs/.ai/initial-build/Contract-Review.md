## Blocking findings and proposed resolutions
1. **Architecture deployment shape — decision resolved 2026-10-24:** The user selected option 2, retaining the nine separate services in System-Architecture.md. This explicit direction supersedes the product baseline's default preference for a modular API plus worker. Recorded in architecture/System-Architecture.md. It is approval of deployment shape only; it does not approve the entire architecture, API contract, cloud provisioning, or a budget increase. Distributed deployment costs and operational feasibility remain to be demonstrated.
2. **API drift:** Contract uses /users/me/quota and /jobs/{job_id}/preview|download; architecture uses /quotas/me and /artifacts/{artifact_id}/preview-url|download-url. Architecture adds /auth/me, consent operations, profile detail/quality override, and admin audit operations. Its upload flow uses POST /artifacts/upload, absent from its public route inventory. Recommendation: choose one public API inventory and keep internal interfaces separate, then align all five architecture documents.
3. **Consent before persistence:** Interaction-Flows.md upload step stores samples before the profile step validates active consent. R-CONS-002 requires documented owner authorization before using or persisting assisted samples. Require active consent/authorization at the sample-upload boundary; never trust a client-supplied user_id.
4. **Enrollment contract mismatch:** API contract accepts inline audio/consent; architecture accepts consent_id and sample_artifact_ids and performs asynchronous quality checks. Define one flow, exact async status/response, actionable findings, informed override, model/version metadata, and status polling before tests are planned (FR-010/011/012, AC-ENR-001).
5. **Idempotency:** AC-GEN-001 supplies a key; the draft makes it optional, duplicates header/body representations, and invents a 24-hour validity. FR-045 alone does not prove that omission must be rejected. Clarify required header, user/operation scoping, request comparison, concurrent submission, durable replay, retention/expiry, and retry after expiry. Recommendation: mandatory Idempotency-Key for generation; retention policy must prevent duplicate execution/billing during the supported retry period. No unsupported fixed duration has been approved.
6. **Quota errors:** Draft gives both 403 and 429 for exhaustion; requirements specify enforcement but not this mapping. Recommendation: distinguish permission denial (403), rate/quota exhaustion (429), and operator budget-stop rejection with a stable error code and agreed HTTP status. Confirm before adopting.
7. **Unsupported constants:** 30 MB upload size, 24-hour token life, one-hour signed URLs, 1000 requests/hour, and idempotency TTL have no explicit requirement/Plan source. Upload duration/script length and expressive-control ranges are missing. They are proposals requiring decisions, not resolved requirements. Model-dependent limits must follow the feasibility protocol.
8. **Contract completeness:** Specify per-operation request/response schemas and content types, absent/null/blank/unknown/read-only handling, malformed versus unknown IDs, numeric/currency precision, stable error codes/statuses, list ordering/filter semantics, pagination, conflict/state transitions, and unsupported-format behavior. Current prose cannot support unambiguous contract tests.
9. **Missing required behavior:** Define regeneration and generated-audio deletion (FR-024, R-WORK-001), model capability/approval gating (R-EXP-001, R-LIC-001), and operator quota/retention/budget configuration boundaries. A listed admin role is not an API or configuration contract.
10. **Security/local setup:** Draft localhost HTTP URL conflicts with its unconditional encrypted-transit statement. Define the local development boundary explicitly while preserving AC-SEC-001 deployment requirements. A signed bearer URL alone does not establish user binding or protection after revocation; define authorization at retrieval and purge/access behavior during cleanup.
11. **Inherited product scope — clarified 2026-10-24:** User confirmed all non-conflicting baseline P0 requirements remain initial-build scope, including FR-013, FR-021, FR-026 and FR-028. The revised Plan.md assigns ownership and acceptance coverage and was approved by the user on 2026-10-24. Proposed numerical NFR targets remain calibration inputs, not silently approved fixed targets. Contract reconciliation can proceed.
